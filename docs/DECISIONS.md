# Decisions & Assumptions

A running log of architectural decisions (lightweight ADRs). Newest phase at the bottom.
Each entry: **Decision** — why — consequences / how to revisit.

---

## Phase 1 — Scaffold

### D-001 Repository layout: light monorepo, no workspace tooling
**Decision:** `apps/web` (Next.js), `contracts/` (Cargo workspace), `supabase/` (SQL migrations + seed), `scripts/` (Node helpers), `docs/`.
The root `package.json` only holds convenience scripts that delegate with `npm --prefix apps/web`.
**Why:** Only one JS package exists today. npm/pnpm workspaces add hoisting complexity for no gain, and
installing inside OneDrive-synced folders is already slow. **Revisit** when a second JS package appears
(e.g. a shared `packages/contracts-client` generated by `stellar contract bindings typescript`).

### D-002 Next.js 16 (App Router) + React 19 + Tailwind v4 + shadcn/ui (Base UI preset)
Latest stable versions at time of writing. Notable Next 16 conventions we follow:
`proxy.ts` replaces `middleware.ts`; `app/manifest.ts` for the PWA manifest; Turbopack by default.

### D-003 One env file: `apps/web/.env.local`
**Decision:** the single env file lives where Next.js natively loads it, `apps/web/.env.local`
(template: `apps/web/.env.example`). `scripts/gen-secrets.mjs` and the contract deploy script write into it.
**Why:** contract IDs produced by the deploy script must reach the web app without copy/paste.
**Rejected:** a repo-root `.env.local` loaded via `@next/env` in `next.config.ts` — tried and verified broken:
`loadEnvConfig` caches Next's own first load and returns early, so root values never reached the build or
runtime (and dev env-reloads would drop them anyway).
Env is validated with zod (`src/lib/env.ts` public, `src/lib/env.server.ts` secrets); secrets never use `NEXT_PUBLIC_`.

### D-004 Testnet first, network is configuration
All Stellar endpoints / passphrase / contract IDs come from env (`NEXT_PUBLIC_STELLAR_NETWORK=testnet`).
Mainnet is a config + key-management change, not a code change (see ROADMAP).

### D-005 Soroban SDK 28, `wasm32v1-none` target
`soroban-sdk = 28.0.0` (MSRV 1.91). Contracts build for `wasm32v1-none`, the target `stellar contract build`
uses for current protocol versions. Release profile is size-optimised with `overflow-checks = true`
(arithmetic overflow must trap, never wrap, in money/capacity code).

### D-006 Three contracts, not one
`event_ticket` (events, tickets, transfers, check-in, revenue split), `rewards` (BY Points token),
`attendance_badge` (POAP). **Why:** independent upgrade paths and smaller WASM; `event_ticket` calls the
other two through cross-contract calls after purchase / check-in and is their only authorised minter
(plus admin).

### D-007 BY Points = custom SEP-41 token contract (not a classic asset wrapped by the SAC)
**Why:** a classic Stellar asset needs a trustline (and 0.5 XLM reserve) per holder — painful for
custodial/email users and for "points" that are meant to be free. A Soroban token implementing the SEP-41
interface works with contract-held balances, no trustline, and lets us add rules (minter allow-list,
optional non-transferability, perk redemption) that a plain SAC admin can't express.
**Trade-off:** points don't show in classic-only wallets. **Alternative kept open:** issue `BYPTS` as a classic
asset and make the `rewards` contract the SAC admin, if exchange-listing / wallet visibility matters later.

### D-008 Custodial fallback for non-crypto users
Email-login users get a server-generated Stellar keypair. The secret is encrypted with AES-256-GCM using
`CUSTODIAL_KEY_ENCRYPTION_KEY` (envelope encryption; swap the key provider for a KMS in production) and stored
encrypted in Supabase; plaintext only exists in memory while signing. Accounts are created/sponsored by the
platform account so users never need XLM. Users can "graduate" to self-custody by linking Freighter.

### D-009 Signed, rotating QR with offline verification (design; implemented in Phase 5)
- Server issues a short-lived **ticket credential**, Ed25519-signed with `QR_CREDENTIAL_SIGNING_KEY`, binding
  `ticket_id`, current owner, and the holder device's public key (non-extractable WebCrypto key).
- The holder's device renders a QR every ~20 s: `credential + timestamp`, signed by the device key.
- Scanners verify **offline** with only the public key `NEXT_PUBLIC_QR_CREDENTIAL_PUBLIC_KEY`, reject stale
  timestamps (screenshots expire), and de-duplicate check-ins locally; queued check-ins sync to the chain via
  `validate_and_check_in` when back online. The contract is the final arbiter of double entry.

### D-010 Payments: USDC/XLM on Stellar, ZMW shown for display, mobile money behind an adapter
Prices are stored in USDC (7-decimal stroop-style integers on-chain). ZMW is a display conversion from an FX
rate (`NEXT_PUBLIC_ZMW_PER_USDC` fallback; pluggable provider later). Mobile money (MTN MoMo, Airtel Money,
Zamtel Kwacha) is behind a `PaymentRampAdapter` interface with a stub implementation only.

### D-011 Rate limiting: Upstash Redis when configured, in-memory fallback
Serverless-friendly; dev works with zero setup. In-memory limits are per-instance, so production must
set `UPSTASH_REDIS_REST_URL`/`_TOKEN`.

### D-012 Supabase new-style API keys
Uses `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…`) and `SUPABASE_SECRET_KEY` (`sb_secret_…`).
Legacy `anon` / `service_role` JWT keys work in the same variables.

### D-014 Contract toolchain runs in Docker (superseded by D-034)
Found during Phase 1: the Windows MSVC toolchain had no linker (VS installed without the C++ workload), and with
the GNU toolchain `cargo test` was blocked by Windows **Application Control (os error 4551)**, which refuses the
unsigned build-script binaries Cargo compiles.
**Decision (chosen by the user):** all contract work runs in a Linux container — `contracts/Dockerfile`
(`rust:1.92-bookworm` + `wasm32v1-none` + rustfmt/clippy + Stellar CLI 28.1.0), driven by `docker-compose.yml`
and the `npm run contracts:*` scripts. Build output, the cargo registry and the Stellar CLI keystore live in
named Docker volumes (fast, outside OneDrive). Same image works on macOS/Linux/CI, so the toolchain is pinned
for everyone.

### D-013 Development inside OneDrive
The workspace lives in a OneDrive-synced folder. That works but makes `npm install` / `cargo build` slow and
can cause file-lock errors. Recommended: move the repo outside OneDrive, or mark `node_modules`, `.next`, and
`contracts/target` as "always keep on this device" / excluded from sync.

## Phase 2 — Contracts

### D-015 Payment token = USDC Stellar Asset Contract; testnet uses a mock USDC by default
`event_ticket` takes the payment token address in its constructor, so it works with any SEP-41 token.
On testnet the deploy script issues its own `USDC` classic asset (issuer = a `by-usdc-issuer` CLI identity)
and deploys its SAC, so we can mint test balances freely. `USDC_MODE=circle` uses Circle's testnet USDC
instead. XLM settlement = deploy with the native XLM SAC as payment token (a second `event_ticket`
instance, or a per-event token in a later version).

### D-016 Classic accounts need a USDC trustline
Because USDC is a classic asset, every **G…** account that receives it (treasury, organizers, artists, buyers,
resale sellers) needs a trustline, otherwise the SAC transfer fails and the whole purchase reverts. Handled:
treasury in the deploy script. To handle: Phase 3/4 create trustlines for custodial accounts (sponsored by the
platform account) and prompt Freighter users; Phase 6 checks split recipients before `create_event`.
Contract (**C…**) addresses don't need trustlines.

### D-017 No per-owner ticket list on-chain
Unbounded per-owner vectors in contract storage get more expensive with every write and are a griefing vector.
The contract stores tickets by id and emits `ticket_minted` / `ticket_transferred`; the app indexes these events
into Supabase for "My Tickets" and always re-checks `get_ticket` on-chain before trusting ownership.

### D-018 `mint_ticket(payer, owner, …)`
Separating payer from owner lets the platform account pay on-chain after an off-chain (mobile money) payment
settles, and lets users buy tickets for friends. Purchase points go to the owner.

### D-019 Paid resale settles on-chain
`transfer_ticket(…, price)` with `price > 0` requires the buyer's auth and moves the payment token buyer → seller
in the same call, so the resale cap is enforced on the actual payment rather than a self-reported number.
Off-chain side payments can't be prevented by any ticketing system; the transfer limit bounds them.
No resale royalty yet (ROADMAP: secondary marketplace).

### D-020 Fee snapshot per event; pause doesn't block check-in
Each event stores the platform `fee_bps` at creation so a later fee change never alters an organizer's agreed
terms. `set_paused(true)` stops sales and transfers (incident response) but `validate_and_check_in` keeps
working so an event in progress isn't stranded at the door.

### D-021 Points and badges are minted by `event_ticket` through cross-contract calls
`event_ticket` is registered as minter on `rewards` and `attendance_badge` (`set_minter`) and passes its own
address as `minter`. A ticket purchase or check-in and its rewards are therefore atomic: no points without
a real purchase or check-in. Badge minting is idempotent per (event, attendee), so a user holding two tickets
for the same event gets one badge.

## Phase 3 — Database & auth

### D-022 Chain is the source of truth; Supabase mirrors it and holds off-chain data
Tables that mirror contract state (`tickets`, `orders`, `ticket_transfers`, `checkins`, `points_ledger`,
`badges`, `redemptions`) store the chain id and tx hash with unique constraints, and are written only with the
service role after the server has verified the transaction (purchase flow in Phase 4, an event indexer later).
Users get read-only access through RLS. The app re-reads `get_ticket` on-chain before trusting ownership
in sensitive flows (QR credential, transfer).

### D-023 Defence in depth: column grants + RLS + triggers
RLS decides *which rows*; it can't stop a user from writing a column on a row they own. So the migration
revokes Supabase's default `GRANT ALL` and grants back per-column `INSERT`/`UPDATE`. That keeps `status`,
`chain_event_id`, `on_chain_approved_at` and review fields out of users' reach. Triggers lock chain-controlled
event and tier fields after publishing. Status transitions (approve, publish, cancel) are RPCs or server
actions that keep the database and the contract in sync.

### D-024 Roles in a `user_roles` table, not JWT custom claims
Simple, auditable, changeable without re-issuing tokens; the policy helpers (`has_role`, `is_admin`) read it via
`SECURITY DEFINER`. Global roles are `customer` (implicit, granted at sign-up), `organizer` (granted on approval),
`scanner` (granted when an organizer adds door staff, Phase 5) and `admin`. Per-event permissions live in
`event_scanners` / event ownership. **Revisit:** a Supabase custom access-token hook if role lookups ever show up
in query plans.

### D-025 Email one-time code as the default sign-in
Many users open email in a different app from their browser (Gmail app vs Chrome), which breaks PKCE magic
links. So the login form asks for the 6-digit code; the email also carries a cross-device `/auth/confirm` link
(template in `supabase/README.md`). No passwords. Wallet sign-in is a signed challenge (D-035)
using `wallet_challenges`.

### D-026 Custodial wallet provisioned at first sign-in, activated on first purchase
Every account gets an encrypted custodial keypair right away (so tickets have an owner address), but
creating the Stellar account and its USDC trustline costs reserves. The platform sponsors that only when the
user first buys (Phase 4, `wallets.activated_at`). Ciphertexts bind the public key as AES-GCM associated
data.

### D-027 Organizer approval is two-step: database role now, contract allow-list in Phase 6
`admin_review_organizer` grants the `organizer` role immediately. The contract's `approve_organizer` needs the
contract admin's signature, and that key lives in the CLI keystore, not the web server. Phase 6 will add an
operator path (either a dedicated operator key in server env with a narrow role, or a queued job run with the
admin identity) and stamp `on_chain_approved_at`. Events can't be published until both are done, because
publishing requires `chain_event_id`.

### D-028 RLS tested against plain Postgres with a Supabase shim
`supabase/tests/supabase_shim.sql` recreates just enough of Supabase (API roles and their default grants,
`auth.users`, `auth.uid()`, `storage.objects`, `storage.foldername`) for the migrations to run in a stock
`postgres:16` container. `npm run db:test` then runs 79 assertions as different users. It's fast and needs no
project or CLI, and the same image generates the TypeScript types (`npm run db:types`, via Supabase's
`postgres-meta`). **Caveat:** the shim isn't Supabase. Re-run the suite against the real project after
applying the migrations (MCP or `supabase test db`).

### D-029 Money columns are `numeric(39,0)` token units
Same 7-decimal integer units as the contracts (i128 fits in 39 digits), so database and chain amounts
compare exactly; formatting to USDC / ZMW happens in `lib/payments/pricing.ts`.

### D-030 Policy helpers live in a `private` schema
The Supabase security advisor (lints 0028/0029) flagged `SECURITY DEFINER` helpers in `public`, because PostgREST
exposes every `public` function as `/rest/v1/rpc/<name>`. Migration `20261026000500_private_helpers.sql` moves
them to `private` (policies reference functions by OID, so they keep working) and revokes direct calls to the
signup trigger functions. The advisor still lists `my_organizer`, `resubmit_organizer` and `admin_*` under 0029:
that's intended, since they are the app's RPCs and check the caller themselves. The 0008 notices ("RLS enabled,
no policy") on `custodial_keys`, `wallet_challenges`, `idempotency_keys` and `chain_cursors` are also intended.

### D-031 External Stellar wallets are proven by signing a one-time message
`/login` and `/account` open Stellar Wallets Kit (Freighter, xBull, Albedo, LOBSTR, Rabet, and other default
modules). The server issues a challenge (32-byte nonce, 5-minute expiry, stored in `wallet_challenges` with
`purpose` `login` or `link`). The wallet signs it (`signMessage`: SEP-53 hash, SHA-256 of the text, or raw UTF-8
are accepted). The server claims the challenge in one conditional `UPDATE` before verifying. The signed text names
the domain, wallet, network and purpose, so a signature can't be reused elsewhere. Linking writes `audit_log`.
Max 3 external wallets per account; the custodial wallet can't be removed. No on-chain transaction is needed.

### D-032 No Docker going forward
The user asked not to use Docker in this project. Supabase work goes through the Supabase MCP (migrations,
advisors, type generation). Contract build and test use the host toolchain (D-034). `npm run db:test` no longer
starts a container; the RLS suite has no local runner. The original testnet admin and mock-USDC issuer keys
remain in the unused `by-stellar-config` volume and are not available to the app.

### D-033 Checkout sells the existing testnet event
Phase 4 lists and sells chain event `1` (Copperbelt Night Live, 100 test USDC, already created by the
smoke test). The contract admin key is not on this machine, so the app does not create a new
on-chain event. Buying pulls USDC from the payer inside `mint_ticket`. The mock USDC `mint` requires the
issuer `GB4RGUGQOUHQXDYV4YJGKXYT7WF5HLCMBSSYDCWHFJ5QAOZ2KYYYXLHG`, which the app does not hold, so a
wallet with no test USDC cannot complete checkout until that issuer signs a mint. The custodial wallet is
created and given a USDC trustline by the platform account. Mobile money uses the in-memory stub: it
settles without contacting a phone, then the platform account pays.

### D-034 Contracts build on the host
D-014 is retired. `npm run contracts:test`, `contracts:lint`, and `contracts:build` call
`scripts/contracts.ps1`, which uses Rust stable (MSVC), the `wasm32v1-none` target, and Stellar CLI 28.1.0.
The Windows SDK 10.0.26100 supplies `kernel32.lib` so the MSVC linker can run. The Stellar CLI binary lives in
`%USERPROFILE%\.local\bin` and is not committed. Deploy and smoke run the existing bash scripts through Git Bash,
with the repo root detected from the script path.
Windows Application Control (os error 4551) still refuses to execute the unsigned build-script programs Cargo
compiles, on both the GNU and MSVC toolchains. Until that policy allows those programs, a host build stops at
the first build script. The GNU toolchain is not a workaround.

### D-035 Sign in with a Stellar wallet
`/login` can create a session from a signed login challenge. If the public key is already linked, that account
is signed in. If it isn't, the server creates an Auth user with a never-deliverable `{g-address}@wallets.invalid`
email (confirmed immediately; no mail is sent), inserts the wallet as `kind=freighter`, then establishes a
Supabase session with `generateLink` + `verifyOtp`. Email OTP sign-in stays. The same wallet cannot belong to two
accounts.
